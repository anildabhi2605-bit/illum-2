# P00-T05 — Baseline acceptance tests and phase gates

**Phase:** P00 — Requirements and baseline freeze  
**Initial status:** NOT STARTED / NOT VERIFIED  
**Task dependency:** P00-T01 through P00-T04.

## 1. Goal
Create traceability from every invariant to a measurable test and phase exit gate.

## 2. Source inputs
Authoritative test matrix; proposed acceptance matrix; all requirement docs.

Use the original requirements as described in `../../01_BASELINE/PRODUCT_RULES_AND_INVARIANTS.md`; read the related feature spec and the source-of-truth files referenced in `../../00_START_HERE/README_START_HERE.md`. If the source does not define a detail, record it as open; do not silently make it part of the approved product behavior.

## 3. Build steps
1. Merge authoritative tests without deleting them.
2. Map every requirement to acceptance IDs.
3. Add tests for local config, approval/version invalidation, project isolation, model fallback, export/deletion and Module E if included.
4. Define what constitutes evidence and who records it.
5. Freeze milestone gates and task status baseline.

## 4. Expected deliverables
Requirement-to-test traceability matrix; release criteria; P00 sign-off.

## 5. Acceptance criteria
No critical invariant lacks a test; missing tests are logged; phase order and status vocabulary are clear.

## 6. Required tests
Coverage review against all sections of original plan; no test marked pass before execution.

Run automated tests first, then required integration/manual tests. Record exact command, environment, result and evidence. Tests that were not executed must be labelled NOT RUN; do not infer pass from implementation appearance.

## 7. Out of scope / prohibited shortcuts
Do not claim planned test cases have passed.

- Do not start the next task automatically.
- Do not change protected skill prompts/contracts without recorded user approval.
- Do not claim a connector/provider is supported without adapter and test evidence.
- Do not log or export secrets.

## 8. Blocker conditions
If original acceptance matrix conflicts with new requirements, record conflict and resolve before freeze.

## 9. Definition of done

- [ ] Prerequisites verified against actual repository state.
- [ ] Code/doc changes are scoped to this task and satisfy approved requirements.
- [ ] Required tests are executed and pass.
- [ ] Regression tests relevant to changed modules pass.
- [ ] Secret, cross-project and destructive-operation risks reviewed where applicable.
- [ ] `../../07_CHANGE_CONTROL/IMPLEMENTATION_STATUS.md` updated with status, evidence path and any blocker.
- [ ] `../../07_CHANGE_CONTROL/CHANGELOG.md` updated if behavior/docs changed.
- [ ] Status is `VERIFIED` only if all required evidence exists; otherwise use `IMPLEMENTED`, `IN PROGRESS` or `BLOCKED`.

## 10. Task report format

When reporting this task, include: initial repo state; requirements used; files changed; design choices; tests and outcomes; acceptance checklist; security/regression impact; status/evidence; remaining blockers; and the next permitted task ID.
